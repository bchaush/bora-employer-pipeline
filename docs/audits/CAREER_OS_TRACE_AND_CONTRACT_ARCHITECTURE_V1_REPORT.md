## 0. Epistemic rules governing this report

Unchanged from Phase C/D/E and reused here without modification, with one scope distinction made explicit (Section 2.2 restates it where it matters):

- Every material claim in this report, and every case/architecture-status label reused from Phase C/D/E, is drawn from the same four-value vocabulary: **OBSERVED**, **RECONSTRUCTED_FROM_DURABLE_EVIDENCE**, **EXPERIMENTAL_NON_CANONICAL**, or **MISSING**. No `UNKNOWN`/`MISSING` evidence state is upgraded. `EXPERIMENTAL_NON_CANONICAL` is a case/architecture-status label (e.g. Phase D's Antigravity benchmark #1 instance) distinct from a trace fact's own `provenance_quality` (Section 2.2), which is a narrower three-value evidence-quality subset of this same vocabulary — the four-label distinction itself is not weakened or dropped, only scoped correctly per Section 2.2.
- **CI regression evals remain conceptually distinct from live production monitoring/incidence** (Phase D/E, reused unchanged). This report makes no production failure-rate, reliability, or frequency claim anywhere.
- This architecture is a conceptual design surface applied over the genuine corpus Phase C/D/E already inventoried, not a claim of completeness over every possible Career OS operating case.
- No case, field, or trace concept is presented as an existing runtime artifact; a conceptual design is never described as `EXECUTABLE_NOW` in the Phase E sense.

## 1. Why this architecture is needed now

Phase D found that Career OS's real failures (e.g. Case `F1-A`'s dual-axis routing gap, Case `F1-B`'s HTTP-200 dead-page false positive, Case `F5-B`'s unproven duplicate-suppression runtime) are frequently **not localizable without reading a chat transcript**: the raw `.career-os/` run artifacts are gitignored and `MISSING`, and reconstruction depends on merged-PR bodies, `CHANGELOG.md`, and `CURRENT_STATE.md` narrative rather than a durable, structured, per-run record. Phase E confirmed the same gap architecturally: several admitted cases (`F1-A`, `F2-A`, `REC-A`) can prove only a narrower `STEP_LEVEL_DIAGNOSTIC` fact today, with no runtime evaluator that reconstructs the full `TERMINAL_END_TO_END` outcome, precisely because no durable, structured trace of the full run exists to inspect.

This report designs the conceptual shape of the fix — `CAREER_OS_RUN_TRACE_V1` (a durable, structured, per-run trace) and a bounded phase/typed-envelope contract (a durable, structured, per-phase-boundary record) — without building either. Per the governing ADR (`docs/decisions/ADR-CAREER-OS-EVAL-HARNESS-SEQUENCE-V1.md`, Section 4, Phase F), architecture comes first; no database, UI, or vendor is preselected.

## 2. `CAREER_OS_RUN_TRACE_V1` — conceptual run trace (no schema file, no implementation)

A run trace is the durable record of one bounded Career OS operating run (e.g. one discovery pass, one package-generation attempt, one controller/reviewer milestone loop). It exists only as a concept in this report — no JSON Schema, Python class, or persisted file is created. Every field below is a **conceptual field**, not a locked schema property name.

### 2.1 Required conceptual fields

| Conceptual field | Purpose | Evidence-honesty rule |
|---|---|---|
| `canonical_sha` | The exact canonical `main` commit the run operated against. | Must be a real, verifiable Git SHA; never inferred from memory. |
| `run_identity` | A stable, durable identifier for this exact run (e.g. the existing `<timestamp>-<short-hash>` convention already used by real closure runs such as `20260907T220348Z-3dacfcfd`, `20260908T184816Z-d3a8a974`, `20260909T172902Z-7add4b47`). | Reused from already-observed repository convention (Phase C/E); no new identity scheme invented. |
| `inputs` | References to the exact inputs the run consumed (e.g. a requisition identity, a fixture path, a milestone contract path) — references only, not a duplicated copy of the source content. | A reference that cannot be resolved is recorded `UNAVAILABLE`, never silently dropped. |
| `sources_attempted` | Every source the run actually tried to consult (e.g. a live employer careers page, LinkedIn Free, Brandeis Handshake), each with its own outcome. | An attempted-but-inaccessible source is recorded `ATTEMPTED_UNAVAILABLE`; a source never attempted is never listed as attempted. |
| `unavailable_sources` | Sources the run could not reach or that do not exist, named explicitly. | Never silently omitted; absence of an artifact is itself a recordable fact (mirrors Phase C's `MISSING` label for gitignored `.career-os/` artifacts). |
| `state_transitions` | An ordered, append-only list of `{from_state, to_state, gate_or_cause, timestamp}` events. | Each transition names its causing gate/decision; a transition with no identifiable cause is recorded `CAUSE_UNKNOWN`, never fabricated. |
| `suppression_reasons` | For any opportunity/action the run suppressed (e.g. `SUBMITTED_OPPORTUNITY_DEDUPE_V1`, `SUPPRESSED_WINDOW` recency cutoff, `BORA_EXCLUDED_EMPLOYER_FAMILY_V1`), the exact doctrine/gate that caused suppression. | Reuses existing named doctrine identifiers (`BLUEPRINT.md` §138.15, §138.6.2, recency bands) rather than inventing a new suppression vocabulary. |
| `model_tool_provenance` | Which agent/tool produced a *consequential* decision (e.g. "ChatGPT classified `role_status=LIKELY_LIVE`"), captured **only where materially relevant to reconstructing that decision** — never a requirement to log hidden reasoning or chain-of-thought. | No hidden reasoning/CoT field exists in this design; only the decision and its attributed source. |
| `human_handoffs` | For each point control passed to Bora: `requested_action`, `context_transferred`, `human_decision_or_confirmation_source` (where available), and `final_outcome`. | Never fabricates machine observability past the human boundary — if Bora's decision process itself was not observed, that is recorded as `HUMAN_ACT_NOT_MACHINE_OBSERVED`, not inferred. |
| `artifact_hashes` | For each artifact the run produced or consumed, a durable identity plus a cryptographic hash (reusing the existing SHA-256 convention already locked for the résumé/cover-letter gold references, `BLUEPRINT.md` §141.13-§141.19). | A missing or gitignored artifact (e.g. a local PDF/DOCX package, per Phase C's finding) is recorded `ARTIFACT_UNAVAILABLE`, never invented or backfilled with a plausible hash. |
| `qa_outcomes` | The result of any deterministic or human QA gate the run passed through (e.g. `evaluate_resume_page_utilization()`, the package-spawn gate, Cursor's review verdict). | Distinguishes a real executed gate outcome from a merely-documented doctrine check, mirroring Phase E's `evaluator_type_owner` distinction. |
| `terminal_state` | The end-to-end outcome the run was actually, observably reached to conclude at. | Never conflated with `first_point_of_divergence` or `first_causal_failure_point` (Section 3). `terminal_state` is a report of what the run's own recorded trajectory ended at, not an assertion that this ending was correct — `terminal_state` itself may be wrong, and a run trace must be able to represent an incorrect `terminal_state` without contradiction. |
| `first_point_of_divergence` | The earliest point in `state_transitions` where the run's actual trajectory departed from the correct trajectory, if any — recorded even when that departure is later caught and corrected; when no instrumented divergence point is identifiable anywhere in the run's own `state_transitions`, the field itself is recorded as `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY` rather than left blank or inferred. When the run's `terminal_state` is correct and no divergence occurred anywhere in its trajectory, `first_point_of_divergence` is instead recorded as `NOT_APPLICABLE` / `NO_DIVERGENCE`, a known-absence label distinct from `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY`, which is reserved for an incorrect `terminal_state` where a real divergence exists but no instrumented point is identifiable. | Recorded independently of `terminal_state`; a run can have a `first_point_of_divergence` yet still self-correct to a correct `terminal_state`, because a later gate (deterministic or human) recovered from it. A recoverable divergence is never labeled `first_causal_failure_point` (see below) merely because it occurred first. When no instrumented divergence point is identifiable anywhere in the run's own `state_transitions` — the causal defect lived in a boundary the trace never instrumented — `first_point_of_divergence` is itself recorded as `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY` (the fully-uninstrumented pair case, Section 3), paired with the same label on `first_causal_failure_point`; this differs from the mixed case where `first_point_of_divergence` is identified as a concrete point A while only `first_causal_failure_point` carries `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY` (Section 3's mixed attribution case) — `first_point_of_divergence` is never inferred or backfilled merely because `first_causal_failure_point` cannot be identified. |
| `first_causal_failure_point` | The earliest point in `state_transitions`, if any, after which the run's incorrect `terminal_state` became unavoidable — i.e. no later gate in the run's own trajectory recovered from it; when no instrumented causal failure point is identifiable — including the mixed case where `first_point_of_divergence` is a concrete point A but no later point B is ever identifiable — the field itself is recorded as `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY` rather than a fabricated point. For any correct `terminal_state`, `first_causal_failure_point` is recorded as `NOT_APPLICABLE` / `NO_TERMINAL_FAILURE` — including when a recovered `first_point_of_divergence` = A is preserved unchanged — never `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY`, because there is no terminal failure to attribute a cause to. | Every identifiable `first_causal_failure_point` is itself an identifiable divergence point — a point where the run's own trajectory departed from correctness — but it equals the run's `first_point_of_divergence` only when no earlier recovered divergence exists in that run's own `state_transitions`. `first_point_of_divergence` always names the *earliest* identifiable divergence point in a run, including one that was later recovered; `first_causal_failure_point` names whichever divergence point actually made the incorrect `terminal_state` unavoidable. In a multi-divergence run these can differ: an earlier divergence A that a later gate caught and corrected, followed by a distinct, later divergence B that no later gate recovered from, yields `first_point_of_divergence` = A and `first_causal_failure_point` = B, at two different points in the same run. A divergence that a later gate caught and corrected is recorded only as `first_point_of_divergence`, never as `first_causal_failure_point`, because it did not make terminal failure unavoidable — this holds whether that recovered divergence was the run's earliest divergence or a later one. A run can also have every intermediate step pass (no identifiable `first_point_of_divergence` in its own instrumented `state_transitions`) and still reach an incorrect `terminal_state`, because the causal defect lived in a boundary the trace never instrumented (Phase D/E's dual-axis invariant, reused unchanged) — in that case **both** `first_point_of_divergence` and `first_causal_failure_point` are recorded with the same symmetric non-identification label, `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY`, never inferred or backfilled for either field alone; the trace never identifies one of the pair while silently leaving the other unlabeled. More generally, whenever no instrumented causal failure point is identifiable in the run's own `state_transitions`, `first_causal_failure_point` is recorded as `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY` — this occurs both in the fully-uninstrumented pair case above (where `first_point_of_divergence` carries the same label) and in the mixed attribution case (Section 3) where `first_point_of_divergence` is instead identified as a concrete, recovered point A; `first_causal_failure_point` is never inferred or backfilled with a fabricated point merely because an earlier divergence was identified. |

### 2.2 Provenance quality on every trace fact

Every fact recorded in a run trace carries its own `provenance_quality`, drawn from the three-value evidence-quality subset of Section 0's four-label vocabulary that actually applies to a trace fact: `OBSERVED` \| `RECONSTRUCTED_FROM_DURABLE_EVIDENCE` \| `MISSING`. `EXPERIMENTAL_NON_CANONICAL` is deliberately excluded from `provenance_quality` — it is not a lower- or higher-quality evidence state a trace fact can carry; it is a case/architecture-status label (Phase D's Antigravity benchmark #1 usage) describing whether an entire instance is granted builder authority, a question a trace fact does not itself answer. This is a scope narrowing, not a vocabulary change: the underlying four-label distinction from Phase C/D/E is preserved unchanged (Section 0); `provenance_quality` simply names the three of those four labels that are coherent for a per-fact evidence-quality marker. A trace is not a single monolithic provenance claim — one run's `canonical_sha` can be `OBSERVED` while its `artifact_hashes` are `MISSING` (gitignored), exactly as Phase C already found for real historical runs. This preserves the acceptance requirement that provenance quality remain distinguishable from reconstructed narrative: a trace fact reconstructed from a merged-PR body or `CHANGELOG.md` entry is never presented with the same evidentiary weight as a fact directly observed from a live run.

### 2.3 Append-only trace facts vs. derived summaries

A run trace's `state_transitions`, `suppression_reasons`, `artifact_hashes`, `qa_outcomes`, and `human_handoffs` are **append-only facts** — once recorded, never rewritten. So are every one of the remaining per-run conceptual fields named in Section 2.1: `canonical_sha` (an append-only fact of which commit the run actually operated against), `run_identity` (an append-only fact of the run's own stable durable identifier, established once at run start and never reassigned), `inputs` (an append-only fact of exactly which input references the run consumed), `sources_attempted` (an append-only fact of exactly which sources the run actually tried, each with its own recorded outcome), `unavailable_sources` (an append-only fact of exactly which sources the run could not reach or that do not exist), `model_tool_provenance` (an append-only fact of which agent/tool produced a given consequential decision, recorded once at the time that decision was made), `terminal_state` (an append-only fact of what the run's own trajectory was actually, observably recorded to end at — recording it does not require it to be correct, only that it be truthfully recorded once), and the `first_point_of_divergence`/`first_causal_failure_point` attribution (Section 3) — an append-only fact about where the run's own recorded trajectory first diverged (`first_point_of_divergence`) and, separately, about whichever divergence point — the same point, or a later, distinct one — after which the run's incorrect `terminal_state` became unavoidable (`first_causal_failure_point`), established from the run's own `state_transitions` and never re-derived from a later narrative. `CURRENT_STATE.md`, `CHANGELOG.md`, and this very report are **derived summaries**: human/ChatGPT-authored narrative *about* trace facts, which may be re-edited, corrected, or superseded (exactly as this repository's own governance files already are, per its own `CAREER_OS_MILESTONE_CONTRACT_AND_STATE_VALIDATION_V1` authority note). A later summary may *reinterpret* an append-only fact (e.g. a future evaluator re-examining a run's `state_transitions` and concluding a different `first_causal_failure_point` attribution than an earlier summary claimed) — but reinterpretation produces a new derived summary, and never rewrites, deletes, or silently supersedes the underlying recorded fact/event itself. This report locks the distinction, not the mechanism: no future implementation may allow a derived summary to silently overwrite or replace the append-only fact it was derived from. This mirrors, at the trace layer, the same append-only discipline `BORA_APPLICATION_HISTORY_V1.json` already enforces at the application-lifecycle layer (Phase E Case `F5-A`).

## 3. Terminal outcome vs. first divergence vs. first causal failure point (not step-level diagnostics alone)

Reused and extended from Phase E Section 2's `TERMINAL_END_TO_END` vs. `STEP_LEVEL_DIAGNOSTIC` distinction: a run trace must be able to record **what actually happened at the end** (`terminal_state`, itself possibly incorrect and never assumed to be "the single correct outcome") separately from **where the trajectory first departed from correctness** (`first_point_of_divergence`) separately again from **the earliest point — which may be that same departure, or a later, distinct divergence — after which the run's incorrect `terminal_state` became unavoidable** (`first_causal_failure_point`). These three are never conflated, and a recoverable divergence is never described as "causally inevitable":

- A run can reach a correct `terminal_state` despite an earlier `first_point_of_divergence` that was caught and corrected by a later gate (e.g. a human catching a stale `role_status` before package time). That divergence is recorded as `first_point_of_divergence` only — it is explicitly NOT a `first_causal_failure_point`, because the run's own trajectory recovered from it and terminal failure was never actually unavoidable.
- A run can have an incorrect `terminal_state` with an identifiable `first_causal_failure_point` — the point after which no later gate in the run's own trajectory recovered. When that run has no earlier recovered divergence, `first_causal_failure_point` coincides with `first_point_of_divergence` at the same point, because nothing upstream diverged first and nothing downstream ever caught the defect.
- A run can contain **more than one divergence point**: an earlier divergence A that a later gate caught and corrected, followed by a distinct, later divergence B that no later gate recovered from. In that run, `first_point_of_divergence` remains A — the earliest identifiable divergence, including a recovered one — while `first_causal_failure_point` is B, the later point that actually made the incorrect `terminal_state` unavoidable. `first_point_of_divergence` and `first_causal_failure_point` are recorded at their own distinct points in this case; `first_causal_failure_point` is never assumed to be the run's `first_point_of_divergence` merely because it is an identifiable divergence point.
- A run can have **no identifiable `first_point_of_divergence`** in its own `state_transitions` (every step diagnostic available passed) and still reach an incorrect `terminal_state`, because the causal defect lived in a boundary the trace never instrumented (exactly Phase D/E's illustrating case: `posting_state_decision_wiring_v1_test.py`'s dual-axis gate passes once `role_status`/`source_verification_status` are already set, but nothing in the current architecture re-derives those axes from a live re-fetch). In that case **both** `first_point_of_divergence` and `first_causal_failure_point` are recorded with the same symmetric non-identification label, `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY` — the trace never identifies one of the pair while silently leaving the other unlabeled, and neither field is inferred or backfilled.
- **Mixed attribution case:** a run can have an identifiable, recovered `first_point_of_divergence` = A (an earlier divergence a later gate caught and corrected, exactly as in the first bullet above) while the actual defect that produced the incorrect `terminal_state` lived in a separate, later, uninstrumented boundary the trace never captured — so no second, later divergence point B is ever identifiable in `state_transitions` to name as `first_causal_failure_point`. In this case `first_point_of_divergence` = A is preserved unchanged (never wiped or reattributed) and separately records `first_causal_failure_point` = `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY`, never inventing a fabricated point B to fill the gap. `first_point_of_divergence` and `first_causal_failure_point` remain independently recorded facts even when one names a concrete point (A) and the other names the symmetric non-identification label — the two are never forced into agreement, and an identifiable recovered A is never treated as evidence that the later, unidentifiable failure must also be A.

- **Success-vs-failure absence semantics:** `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY` is reserved exclusively for an incorrect `terminal_state` where a real divergence or causal failure genuinely exists but no instrumented point in the run's own `state_transitions` can identify it — it is never used to describe the simple absence of any divergence or failure. A run with a correct `terminal_state` and no divergence anywhere in its trajectory records `first_point_of_divergence` = `NOT_APPLICABLE` / `NO_DIVERGENCE`, a known-absence label distinct from `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY`'s unknown-cause label. For any correct `terminal_state` — whether or not an earlier divergence occurred — `first_causal_failure_point` is recorded as `NOT_APPLICABLE` / `NO_TERMINAL_FAILURE`, because there is no terminal failure for a causal point to explain; when a recovered `first_point_of_divergence` = A exists alongside a correct `terminal_state`, `first_point_of_divergence` = A is preserved unchanged (exactly as in the recoverable-divergence case above) while `first_causal_failure_point` = `NOT_APPLICABLE` / `NO_TERMINAL_FAILURE` applies instead of `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY`. `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY` never appears on a correct-terminal success case for either field. The pre-existing identifiable A→B failure case, the mixed failure case (`first_point_of_divergence` = A with `first_causal_failure_point` = `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY`), and the fully-uninstrumented incorrect-terminal pair case (both fields `CAUSE_UNKNOWN` / `UNINSTRUMENTED_BOUNDARY`) remain preserved unchanged, because all three describe an incorrect `terminal_state`, not a correct one.

This is precisely why Phase D/E found several cases where a passing `STEP_LEVEL_DIAGNOSTIC` (Case `F1-A`, Case `F2-A`) could not be presented as terminal coverage: a run trace, once it existed, would let a future evaluator ask "was there a `first_point_of_divergence` upstream of this passing step, and, if so, was that same point (or a later, distinct point) the run's `first_causal_failure_point`" instead of only asking "did this one step pass."

## 4. Human-handoff architecture

A `human_handoffs` entry (Section 2.1) exists only for a genuine control-passing event to Bora — the human — never for a model/tool decision. Recording that ChatGPT (or any other model/tool) made a consequential classification or adjudication is `model_tool_provenance`'s job (Section 2.1, Section 7), not `human_handoffs`; the two are never merged into one entry type, because `model_tool_provenance` describes a machine-observable decision-and-source pair while `human_handoffs` describes the boundary past which Career OS cannot machine-observe further. A `human_handoffs` entry exists for every point where Career OS hands control specifically to Bora rather than resolving something itself — pursuit approval, submission, an ambiguous immigration/legal fact (`BLUEPRINT.md`'s `LEGAL_VERIFICATION_REQUIRED` boundary), or a semantic adjudication that requires Bora's own judgment. Each entry records:

- `requested_action` — what Career OS asked Bora to decide or confirm.
- `context_transferred` — the exact evidence/references handed to Bora at that moment (never a claim about what Bora actually read).
- `human_decision_or_confirmation_source` — where available, the durable record of Bora's decision (e.g. `BORA_APPLICATION_HISTORY_V1.json`'s `evidence_basis: BORA_DIRECT_CONFIRMATION`, or an explicit Bora statement recorded in a checkpoint/changelog, per the pattern this very roadmap already uses for phase authorization/acceptance).
- `final_outcome` — the resulting state after the handoff.

This design explicitly does **not** fabricate machine observability past the human boundary. Phase E's Case `POS-A` (the 14-entry submitted-application ledger) is the load-bearing precedent this design generalizes: the ledger's own structural integrity is machine-checkable (`EXECUTABLE_NOW` via `tests/application_history_registry_v1_test.py`), but Bora's actual submission act is `HUMAN_CONFIRMED_REFERENCE` — never `EXECUTABLE_NOW`, never described as machine-observed reasoning. A `human_handoffs` entry whose `human_decision_or_confirmation_source` cannot be established is recorded `HUMAN_ACT_NOT_MACHINE_OBSERVED`, exactly mirroring `MISSING`/`UNKNOWN` discipline elsewhere in this architecture — it is never silently inferred from context alone.

## 5. Bounded phase/typed-envelope contract (per phase boundary, not per whole run)

Distinct from a whole-run trace (Section 2), a **phase contract** is the conceptual typed envelope crossing one bounded phase boundary inside a run (e.g. one controller step, one reviewer pass, one deterministic gate call) — the concept the governing ADR's IndyDevDan reference frame names as "structured/typed envelopes cross seams" (Section 2 of the ADR, `CAREER_OS_ADAPTATION`). Every phase contract carries, conceptually:

| Conceptual field | Purpose |
|---|---|
| `phase_id` | Which bounded phase/step this envelope belongs to. |
| `input_refs` | References to this phase's inputs (not duplicated payloads). |
| `output_refs` | References to this phase's outputs. |
| `decision_or_state` | The state/decision this phase actually produced (e.g. a `Job.decision` value, a gate PASS/FAIL). |
| `evidence_or_provenance_refs` | Which Evidence_ID(s)/Claim_ID(s)/durable artifact(s) this phase's decision rests on, per `BLUEPRINT.md`'s Evidence_ID rule (Section 10) — never a decision with no lineage. |
| `gate_outcome` | The specific deterministic or human gate result that authorized (or refused) the transition out of this phase. |
| `error_or_unavailable_state` | An explicit failure/unavailable marker if the phase could not complete normally — never silently absent. |
| `authority_or_handoff_metadata` | Which authority (deterministic code, a specific agent, or Bora) actually authorized this phase's transition, matching this repository's existing Authority Order (`AGENTS.md`). |

A phase contract is strictly narrower than a run trace: many phase contracts compose into the `state_transitions` of one run trace. This report locks the conceptual shape only; no envelope serialization format, validation library, or runtime wiring is authorized here.

## 6. Artifact references: durable identity plus hash semantics

Reused unchanged from the already-locked résumé/cover-letter gold-reference convention (`BLUEPRINT.md` §141.13-§141.19: SHA-256 `264f7a8c...`/`0b7da431...`): any artifact a trace or phase contract references must be identified by a durable identity (a stable name/path/run-identity) plus, where the artifact still exists, a cryptographic hash. Where the artifact is gitignored, deleted, or never durably captured (Phase C's repeated finding for `.career-os/` run artifacts and local PDF/DOCX packages), the reference is recorded `ARTIFACT_UNAVAILABLE` — this architecture never invents a hash or backfills a plausible one for an artifact that cannot be independently re-verified.

## 7. Model/tool provenance — materiality boundary, no hidden reasoning requirement

`model_tool_provenance` (Section 2.1) is recorded **only where materially relevant to reconstructing a consequential decision** — e.g. recording that ChatGPT (not a deterministic gate) classified a posting's `role_status`, because that classification is exactly the axis Phase D/E found under-instrumented. This design does not require, and explicitly does not authorize, storing an agent's hidden reasoning, chain-of-thought, or full conversational transcript. The trace records the decision and its attributed source, never the reasoning process that produced it.

## 8. CI regression evals vs. live production monitoring/incidence (reused unchanged)

Exactly as Phase D (§4, §9, §10) and Phase E (§7) already lock: this architecture's own future test coverage (Section 9 below) would be a **CI regression eval** if ever implemented, never a live production monitoring/incidence layer. No trace field, phase-contract field, or design decision in this report constitutes or implies a claim about how often any failure mode actually recurs during real, ongoing Career OS operation. This report makes no production failure-rate or reliability claim anywhere.
